# 在线协同文档编辑器项目规划书

## 一、项目概述

### 1.1 项目名称

在线协同文档编辑器

### 1.2 项目定位

一款轻量化Web在线文档系统，支持多人实时协同编辑，同时兼容普通文本、代码编辑场景；提供文档目录管理、权限控制、版本快照、文档分享能力。面向小组内部协作场景，区别于复杂的飞书/语雀，重点实现核心协同逻辑，适合作为前端/全栈项目，突出 WebSocket、并发冲突处理、Monaco 编辑器集成等技术难点。另附一个轻量的数据可视化（ECharts）与画布（Canvas）演示模块，用于展示文档使用情况统计，属于锦上添花的加分项，不影响协同主链路。

### 1.3 项目目标

1. 用户登录鉴权，文档隔离，私有文档仅本人可见
2. 基于 Monaco Editor 实现代码/富文本混合编辑
3. WebSocket 实时同步编辑操作，多人协同
4. 简易 OT 操作转换方案，解决并发编辑冲突
5. 文档权限：私有、只读分享、可编辑分享
6. 文档版本快照保存、历史版本查看与回滚
7. 文档目录树管理，新建、重命名、删除、文件夹归类
8. 分享链接生成、过期时间配置
9. 文档数据可视化：统计文档数量、在线协同人数、编辑频次，用 ECharts 渲染折线 / 柱状 / 饼图
10. 简易画布批注（Canvas 2D）：画笔、橡皮、清空，作为独立演示页面

### 1.4 技术栈

- 前端：Vue3 + Element Plus + Pinia + Vue Router4 + Axios + Monaco Editor + Socket.io-client + Markdown-it
- 前端可视化：ECharts（统计图表） + 原生 Canvas 2D API（画布批注，无需额外依赖）
- 后端：Node.js + Express + Socket.io + MySQL
- 辅助：JWT鉴权、Multer（可选，文档附件）、Git、Prettier
- 协同核心：简易 OT（Operational Transformation）操作转换模型

## 二、需求分析

### 2.1 用户角色

1. 普通登录用户：创建文档、编辑自己文档、管理目录、生成分享链接、查看自己的版本记录、查看个人文档统计
2. 访客：通过分享链接访问文档，权限由分享配置决定（只读 / 可编辑）

### 2.2 功能需求列表

#### （1）账号模块

- 用户注册、登录、退出
- JWT 令牌，路由守卫拦截未登录访问
- 令牌过期自动刷新、异常捕获

#### （2）文档目录管理模块

- 树形目录：文件夹、文档两级结构
- 新增文件夹、新增文档、重命名、移动、删除
- 目录持久化存储

#### （3）编辑器核心模块

- Monaco 编辑器嵌入，支持代码语法高亮、自动换行
- 文档内容本地缓存，防止刷新丢失
- 光标位置同步：协同用户显示其他在线用户光标、用户名标识

#### （4）实时协同模块（重点难点）

- WebSocket 长连接，文档打开时加入房间（roomId=文档id）
- 本地编辑生成操作（op）：插入、删除、替换
- OT 转换：本地操作与远端并发操作进行变换，保证所有客户端最终状态一致
- 操作节流，避免高频输入刷屏推送
- 在线成员列表展示

#### （5）文档分享模块

- 生成分享链接
- 权限选择：只读 / 可编辑
- 设置链接过期时间
- 链接访问校验

#### （6）版本快照模块

- 手动保存快照（也可配置定时自动快照）
- 快照记录：版本号、操作人、时间、文档完整内容
- 版本列表查看、预览、一键回滚到指定版本

#### （7）数据可视化与画布模块（轻量加分项）

> 定位：独立页面，与协同主链路解耦，数据只读展示，不做实时大屏。

- 统计概览卡片：文档总数、文件夹数、近 7 天编辑次数、当前在线协同人数
- ECharts 折线图：近 7 天编辑频次趋势（x 轴为日期，y 轴为编辑次数）
- ECharts 柱状图：按文档维度统计编辑次数 Top 5
- ECharts 饼图：文档权限分布（私有 / 只读分享 / 可编辑分享）
- 原生 Canvas 画布批注页：画笔自由绘制、橡皮擦、清空画布、导出 PNG；绘制逻辑全用 Canvas 2D API 手写
- 图表数据来源：后端统计接口一次性查询，进入页面时渲染，不做高频轮询

### 2.3 非功能需求

1. 实时性：输入操作延迟控制在 300ms 以内
2. 稳定性：网络断连后自动重连，重连后同步最新文档状态
3. 兼容性：Chrome、Edge 主流浏览器
4. 性能：单文档协同人数控制在 10 人以内（Demo 规模）；图表页面渲染耗时控制在 500ms 内，图表实例离开页面必须 dispose
5. 安全性：分享链接校验、私有文档鉴权、SQL 防注入

## 三、总体架构设计

采用前后端分离架构，HTTP 负责常规 CRUD，WebSocket 负责实时协同通信。统计接口同样走 HTTP，与 Socket 通道完全解耦。

```
客户端(Vue3) <--HTTP--> Express后端(用户、文档、快照、分享、统计接口)
客户端(Vue3) <--Socket.io--> Express Socket服务(协同房间、操作同步、OT计算)
后端 <--> MySQL（用户、文档、目录、快照、分享记录、编辑日志）
```

### 3.1 前端分层

1. 路由层：登录页、文档首页（目录）、编辑页、分享访问页、统计页、画布批注页
2. 状态层：Pinia 维护用户信息、当前文档、在线成员、连接状态、统计数据
3. 组件层：目录树组件、Monaco编辑器封装组件、在线成员面板、版本弹窗、分享弹窗、统计图表组件（ECharts 封装）、画布组件（Canvas）
4. 服务层：axios 请求封装、socket 服务封装、OT工具类封装、图表初始化与销毁工具、Canvas 绘制工具

### 3.2 后端分层

1. 路由控制器：用户、文档、文件夹、快照、分享、统计
2. Socket 服务：房间管理、消息分发、OT 变换计算
3. 数据库层：model 模型
4. 中间件：JWT鉴权、全局异常处理、跨域

### 3.3 数据库表设计（核心表）

1. user 用户表：id, username, password, create_time
2. folder 文件夹表：id, name, parent_id, user_id, create_time
3. document 文档表：id, name, folder_id, user_id, content（文本）, status
4. doc_snapshot 文档快照表：id, doc_id, content, remark, create_time, user_id
5. doc_share 分享表：id, doc_id, share_code, permission, expire_time, create_time
6. doc_edit_log 编辑日志表（为统计服务）：id, doc_id, user_id, action（insert/delete/save）, create_time

## 四、模块详细设计 & 开发顺序（迭代计划）

> 总周期：4 个必做迭代 + 1 个可选加分迭代，适合个人独立开发

### 迭代一：基础骨架与账号、目录（1~3天）

目标：跑通项目基础，完成登录、目录CRUD

1. 前端初始化 Vue3 + Element Plus + Pinia + Router
2. 后端 Express 基础框架，MySQL 建表
3. 注册登录接口、JWT鉴权
4. 目录树形组件、文件夹/文档增删改查
5. 路由守卫，未登录跳转登录页

输出：可以登录、创建文件夹、新建空白文档，点击文档跳转到编辑器页面（编辑器空白）

### 迭代二：Monaco编辑器集成 + 文档基础读写（2~3天）

目标：实现单人编辑，文档内容保存加载

1. 封装 Monaco 组件，配置主题、语言
2. 文档保存、文档内容查询接口
3. 编辑器内容变更监听，防抖保存
4. 本地缓存兜底

输出：单人可以正常编辑、保存文档，关闭页面重新打开内容不丢失

### 迭代三：WebSocket协同 + OT并发处理（核心难点，3~5天）

目标：多人协同编辑，解决冲突

1. Socket.io 服务搭建，按文档ID创建房间
2. 封装操作 OP 结构：{type:insert/delete, pos, text, len, userId}
3. 实现简易 OT 变换函数（两个并发操作转换）
4. 本地产生操作 → 发给服务端 → 服务端广播给房间其他人
5. 远端收到操作后，和本地未确认操作做 OT 变换，再应用到编辑器
6. 在线成员列表、断线重连机制

输出：打开两个浏览器，进入同一个文档，可以互相看到输入，并发修改不会错乱

### 迭代四：分享、版本快照、优化收尾（2~3天）

1. 分享链接生成、权限校验、访客页面
2. 快照保存、版本列表、回滚功能
3. 全局异常处理、loading、错误提示
4. 代码整理、注释、打包部署（本地）
5. Bug修复、性能优化（操作节流）

### 迭代五：数据可视化与画布（可选加分项，1天）

目标：补齐统计图表与画布演示，作为简历/答辩展示亮点

1. 后端统计接口：文档总数、文件夹数、近7天编辑次数、在线人数
2. 编辑日志埋点：保存文档、协同 OT 应用成功时写一条 doc_edit_log
3. 安装 ECharts，封装通用图表组件（初始化、resize、dispose）
4. 统计页：概览卡片 + 折线图 + 柱状图 + 饼图
5. 画布批注页：Canvas 画笔、橡皮、清空、导出 PNG（纯原生 API，不引第三方库）

输出：一个独立统计页面能正常展示四类图表，画布页可自由涂鸦并导出图片

## 五、难点与解决方案

| 难点 | 方案 |
| --------------------- | ------------------------------------------------------------ |
| 多人同时编辑内容冲突 | 实现轻量 OT 模型，不引入复杂库，自己维护 op 变换逻辑，面试重点讲 |
| Monaco 和协同操作对接 | 监听编辑器 change 事件，把原生变更转为自定义 OP 对象；远端 OP 再转化为编辑器 delta 操作 |
| WebSocket 断网 | 监听 disconnect，自动重试连接；重连成功后拉取最新文档状态，补发未同步操作 |
| 高频输入消息过多 | 前端节流，短时间连续输入合并操作，减少推送频次 |
| 权限安全 | 所有 socket 消息附带 token，服务端校验当前用户是否有权限操作该文档 |
| 图表页在协同页面频繁重建导致卡顿 | 统计页做成独立路由，进入才初始化；组件卸载时 `chart.dispose()`；窗口 resize 用防抖监听；容器必须给定固定宽高 |
| Canvas 绘制与坐标偏移 | 绘制前按 `devicePixelRatio` 缩放画布，坐标用 `getBoundingClientRect()` 换算，避免高 DPI 屏笔迹错位 |
| 统计口径不准 | 编辑日志只在「保存」和「OT 应用成功」两个时机埋点，避免每次按键都写库 |

## 八、风险说明

1. OT 本身复杂度较高：个人Demo不需要做到工业级完善，**重点讲清楚原理和自己实现的简化方案**，面试官很认可；可以提前说明场景限制（人数不多、纯文本/代码协同，不支持富文本复杂格式）
2. Monaco 体积偏大：开发环境正常使用，打包可配置按需引入减小体积
3. ECharts 体积与按需引入：全量引入会让包体变大，可只引 `echarts/core` + 折线/柱状/饼图模块，避免拖慢首屏
4. 可视化模块属于加分项，务必放在迭代五，**不能挤占协同核心的时间**；时间紧张时可直接砍掉
